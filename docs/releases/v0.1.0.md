# agent-autosuggest-corpus v0.1.0

**Released 2026-10-17. The first release.** One Python package, `agent-autosuggest-corpus`, and one
image, `docker.io/oramasearch/agent-autosuggest-corpus:v0.1.0`.

The Auto-Suggest Corpus Agent writes supervised fine-tuning examples for the Auto-Suggest model. One example is a **profile** (a
persona with its constraints, connections with capture state, tables with schemas and null rates)
paired with a **project profile**: what is worth building on that data (`suggested`) and what is not,
and why (`declined`). The project profile is the shape the project-creation agent consumes. Every
example is checked against the eval set (`agent-eval-generator`'s profiles, the test set for this
model) so the corpus never overlaps it, and against the workspace's methodology and solution
registries so it teaches only what the engine can run.

It runs two ways: as a batch CLI that grows the corpus file in this repository, and as a Lake library
agent that answers one checked example per turn and writes nothing to the corpus.

This tree is the same as commit `a882954` (the image every Lake runs today, below) plus these notes,
the release test and the `version` field of `/healthz`.

## What it includes

### The generator (`agent.py`)

- **`generate_one`**: one model call with the system prompt, the registries as context, the eval set's
  industries listed as off-limits (and, in the CLI, the examples already generated this run), then:
  parse the JSON, the contamination guard, registry enforcement, the defect checks. It returns the
  example or the reason it was not kept.
- **Prompt version `v3`** (`PROMPT_VERSION` in `agent.py`, file `prompts/v3.md`). `v1.md` and `v2.md`
  remain in the package but are not used. Every kept example records `prompt_version`.
- **The contamination guard** (`guard.py`, `EvalGuard`): loads every `*/profile.json` under the eval
  profiles directory and rejects a candidate whose `profile_id` or industry is in the eval set, or
  whose industry and table names overlap an eval profile by more than 60% (Jaccard of words of four
  letters or more). With no eval set loaded it rejects everything.
- **Defect checks** (`_defects`): every constraint must narrow the answer (a number, a prohibition or
  an ordering word); a suggestion is required when a runnable solution exists; something must be
  declined when the solution registry is not empty; every suggestion says why the data supports it;
  a forecast is never calibrated; a supervised suggestion has a holdout; `solution` is a catalogue id
  (`S-n`, `B-n`, `M-n`, `UC-n`); `fits_the_constraint` does not restate a constraint; a declined
  item's answer matches its reason (*capture it first* only for an uncaptured source).
- **Methodology registry** (`methodologies.py`): copies each item's `runnable` from the registry,
  moves non-runnable suggestions to `declined` with `not supported yet`, `needs M-n` and the
  registry's tracking issue, and rejects unknown ids.
  [Methodology contract](../methodologies/README.md).
- **Solution registry** (`solutions.py`): copies `runnable`, derives the ordered methodology
  composition for the chosen capability level (`minimum_level`, `pipeline_order`, the `primary`
  entry), moves non-runnable solutions to `declined` with `needs S-n`, never suggests a band-B
  sketch, and validates level, composition and primary methodology.
  [Solution contract](../solutions/README.md).
- **Replay** (`replay`): runs the same defect checks over a stored JSONL corpus against the fixtures.

### The corpus

`corpus/autosuggest-sft-v3.jsonl`: **one** replay-validated example (prompt v3). It is not in this
repository's image. It is the named build context `corpus` of
[agent-autosuggest](https://github.com/oramasearch/agent-autosuggest)'s image, which copies
`autosuggest-sft-v3.jsonl` as its retrieval corpus. `corpus/README.md` is its data card.

### Registry fixtures (offline generation and replay)

- `fixtures/methodologies.json`: M-1 (churn / GBDT classification), runnable; nothing else.
- `fixtures/solutions.json`: S-1, runnable, and S-2, deliberately non-runnable, so both the
  recommendation and the refusal paths are exercised.

### CLI entry points (`[project.scripts]`)

| Command | What it does |
|---|---|
| `agent-autosuggest-corpus` | Batch generation: `--examples N` (default 5), `--model` (default `$AUTOSUGGEST_MODEL` or `gpt-4o`), `--out` (default `corpus/`, appends to `autosuggest-sft-v3.jsonl`), `--eval-profiles` (default `$EVAL_PROFILES`; refuses to run without an eval set), `--methodologies-fixture`, `--solutions-fixture`. `--replay <file>` validates a corpus against the fixtures with no model call. Calls OpenAI directly (`OpenAI()`, reading `OPENAI_API_KEY`) because it runs for no workspace |
| `agent-autosuggest-corpus-serve` | The Lake library agent: the HTTP server below, plus the agent bus worker when configured |

### HTTP API (`service.py`)

| Route | Answer |
|---|---|
| `GET /healthz` | `200 {ok: true, agent, version, eval_profiles}` with the eval set loaded; `503` with `ok: false` without it, since no turn can be answered then |
| `POST /v1/turn` | One turn. `Authorization: Bearer $AGENT_SERVICE_TOKEN` is required when that variable is set. `200` with the answer when `ok`; `422` with `{ok: false, error}` otherwise; `400` for a body that is not JSON; `401` for a wrong token |

Anything else is `404`.

**One turn** (`run_turn`) takes a JSON object. It reads `request` (or `message`), the person's
steer ("a quality manager at a contract bakery"); `lake_token` and `customer_id`, which select the
live registries; and `lake_url` (or `$LAKE_URL`) with `lake_token` for the model. The turn `kind` and
`workspace_id` are not read. It:

1. refuses without the eval set;
2. reads the methodology registry (`list_methodologies`) and the solution registry
   (`list_solutions`, then `get_solution` for each id) through Lake's `POST /v1/workspace_query`, with
   the turn's `lake_token` and `customer_id` and `$LAKE_URL`. Without all three it uses the fixtures.
   An `unknown_capability` answer means an older engine: M-1 only for methodologies, an empty
   solution catalogue. Any other registry error fails the turn;
3. makes up to two attempts (`ATTEMPTS = 2`) at `generate_one`, with the model reached through
   Lake's model gateway (below);
4. answers `{ok: true, reply, result: {kind: "autosuggest_example", example, prompt_version}}`, or
   `{ok: false, error}` with the reasons. It writes nothing to the corpus.

### Lake capabilities it calls

| Capability | Through | Why |
|---|---|---|
| `receive_agent_tasks` | `GET <LAKE_URL>/v1/receive_agent_tasks`, `AGENT_BUS_TOKEN` | Long-poll its task topic |
| `claim_agent_task` | `POST <LAKE_URL>/v1/claim_agent_task`, `AGENT_BUS_TOKEN` | Take a task and receive its body |
| `publish_agent_event` | `POST <LAKE_URL>/v1/publish_agent_event`, `AGENT_BUS_TOKEN` | `progress`, then `result` or `failed` |
| `workspace_query` → `list_methodologies` | `POST <LAKE_URL>/v1/workspace_query`, the turn's `lake_token` | The methodology registry |
| `workspace_query` → `list_solutions`, `get_solution` | the same | The solution catalogue, hydrated |
| Model gateway (`<lake_url>/openai/v1`, chat completions) | the OpenAI client with the turn's `lake_token` as the API key (`model.py`) | The model call; Lake counts its tokens in the turn's workspace and enforces the account's model-token limit |

### How Lake reaches it

- **The operator runs it as a library agent** of every Lake: one Deployment and one Service, port
  `8080`, health on `/healthz`. Lake learns its address from `LAKE_AGENT_ENDPOINTS`
  (`agent-autosuggest-corpus=<url>`). Lake's catalogue lists it as the Auto-Suggest Corpus Agent, a
  testing agent that Ask Orama hands corpus requests to (lake `docs/api/train-agents.md`).
- **Turns arrive on the agent bus** (`lake_bus.py`, lake `docs/api/agent-bus.md`). Lake publishes each
  turn as a task on `agent-tasks.agent-autosuggest-corpus` of Lake's own Zetta; the topic carries the
  task id, never content. Lake puts the person's message in the task body as `request`, with
  `lake_token` (the task credential) and `lake_url`. What this code does:
  1. at startup, when `LAKE_URL`, `AGENT_BUS_TOKEN` and `AGENT_BUS_AGENT` are all set, a background
     thread starts; otherwise it logs that the bus is not configured and only `POST /v1/turn` works;
  2. the thread long-polls `receive_agent_tasks` with `wait_ms` 10000, from sequence 1 at every start,
     continuing from `next_sequence`; a failed receive waits 2 seconds and retries;
  3. for each task it calls `claim_agent_task`. A `conflict` or `not_found` means another replica won,
     and the task is skipped. The claim's `customer_id` is copied into the turn when the body has none;
  4. up to four claimed turns run at once (a thread pool). Each publishes one `progress` event
     ("Working on it"), runs `run_turn`, and publishes `result` with the whole answer, or `failed`
     with the error. An exception in a turn becomes a `failed` event, not a dead worker.

  It sends no heartbeat (Lake renews the lease on each capability call made with the task credential), and sends no `workspace_id` (Lake uses the
  task row's own; see known issues).

## What it does not include

- **A corpus of useful size.** The active corpus is one example. The 17 v1 rows were removed because
  their free-form methodology labels could not be checked against the registry; the v2 row lacked
  solution facts.
- **Corpus writes from Lake.** A Lake turn returns one example and adds nothing to the corpus file;
  growing the corpus is the batch CLI's, run by hand with an OpenAI key.
- **Training.** Nothing has been trained on this corpus, so there is no evidence yet that it teaches
  what it intends to.
- **Real data.** Every situation is synthetic; none is drawn from a customer.
- **Live registries offline.** The CLI and replay use the fixtures (M-1; S-1 and a non-runnable S-2),
  not a workspace's registry.
- **High yield.** Roughly half of generations are rejected, mostly for vague constraints, so kept
  examples skew toward what the model finds easy to constrain.
- **Usage reporting of its own.** Model tokens are counted by Lake's gateway.

## Known issues

Security-relevant first.

1. **`POST /v1/turn` is unauthenticated when `AGENT_SERVICE_TOKEN` is unset.** The operator always
   sets it on library agents; a pod run another way must set it too.
2. **The task's workspace is not passed explicitly**:
   receive, claim, publish and `workspace_query` carry no `workspace_id`. Lake scopes the task
   credential to the task's workspace, so a turn cannot reach another workspace, but the issue also
   asks for an idle receive at most once a minute; this agent long-polls every 10 seconds.
3. **The lease is kept by activity only.** The agent sends no heartbeat of its own. Lake renews a claim's lease on every accepted event and every capability call made with the task credential (lake [`docs/api/agent-bus.md`](https://github.com/oramasearch/lake/blob/dev/docs/api/agent-bus.md)), so a turn can be reclaimed only if a single step between two such calls, such as one model call, outlasts `lease_seconds` (600 seconds by default). Not observed.
4. **The receive cursor is in memory.** Each start reads from sequence 1; tasks already claimed are
   filtered by Lake, so this costs a larger first read, not duplicate work.
5. **The registries are read from `$LAKE_URL`**, while the model call prefers the turn's `lake_url`.
   Both point at the same Lake today.
