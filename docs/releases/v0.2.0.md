# agent-autosuggest-corpus v0.2.0

**Released 2026-10-25. A minor release.** Two security fixes from the 2026-10-21 security review
since [v0.1.0](v0.1.0.md). Both change behaviour for a service run outside the operator, which is
why this is a minor release and not a patch. Private repository and image,
`docker.io/oramasearch/agent-autosuggest-corpus:v0.2.0`.

This release is the tree of `dev` at `47fe077` with these notes and the version. Release tracking:
[#16](https://github.com/oramasearch/agent-autosuggest-corpus/issues/16).

### The service token is always required, compared in constant time — #12

- `POST /v1/turn` checks `Authorization: Bearer <AGENT_SERVICE_TOKEN>` with `hmac.compare_digest`
  over bytes (`turn_refusal()` in `service.py`) instead of `!=`, which leaked timing.
- It **fails closed**: with `AGENT_SERVICE_TOKEN` unset or empty, every turn is refused with `503`.
  In v0.1.0 the route was open to anyone who could reach the pod. A wrong or missing bearer is still
  `401`.
- Turns from Lake's agent bus do not go through this route and are unaffected.

### A turn's credential goes only to `LAKE_URL` — #14

- In v0.1.0 the model gateway address came from the turn's `lake_url`, falling back to `LAKE_URL`, so
  whoever could submit a turn could have the service send the turn's Lake bearer to a host of their
  choice.
- Now `lakes_url()` reads `LAKE_URL` from the environment and accepts only an absolute `http(s)` URL
  with no user info. The model is reached only at `<LAKE_URL>/openai/v1`; the turn's `lake_url` is
  ignored. The registry reads already used `LAKE_URL` only, and a test now holds them to it.
- With `LAKE_URL` unset or unusable, a turn is refused (`LAKE_URL is not set: ...`) before any request
  goes out, on both `POST /v1/turn` and the bus.

## Before it rolls: the settings it needs

| Variable | Change |
|---|---|
| `AGENT_SERVICE_TOKEN` | Now **required** for `POST /v1/turn` (`503` without it) |
| `LAKE_URL` | Now **required** for every turn (an absolute `http(s)` URL, no user info) |

Nothing new: the Orama operator already renders `AGENT_SERVICE_TOKEN`, `LAKE_URL` and `AGENT_MODEL`
on every library agent, so no operator release has to roll first. A service run by hand must set
both. The other variables are unchanged from [v0.1.0](v0.1.0.md#environment-variables).

## What it does not include

Unchanged from [v0.1.0](v0.1.0.md#what-it-does-not-include): a corpus of useful size (the active v3
corpus is still one example), corpus writes from Lake, training, real data, live registries offline,
high yield, and usage reporting of its own.

## Known issues

Security-relevant first. All open at this tag.

1. **The task's workspace is not passed explicitly**
   ([#6](https://github.com/oramasearch/agent-autosuggest-corpus/issues/6)): receive, claim, publish
   and `workspace_query` carry no `workspace_id`. Lake scopes the task credential to the task's
   workspace, so a turn cannot reach another workspace. The issue also asks for an idle receive at
   most once a minute; this agent long-polls every 10 seconds.
2. **Corpus drafts from Lake fail validation for S-1**
   ([#15](https://github.com/oramasearch/agent-autosuggest-corpus/issues/15)): asked through Ask
   Orama on lake-dev, the generated examples did not choose a registry level for solution S-1, the
   validator rightly refused them, and the turn failed with nothing created. The generation prompt
   does not carry each solution's `capability_levels`, and the agent does not repair and retry before
   failing. Not fixed in this release.
3. **The lease is kept by activity only.** No heartbeat of its own; Lake renews the lease on each
   accepted event and capability call made with the task credential. Not observed.
4. **The receive cursor is in memory.** Each start reads from sequence 1; Lake filters claimed tasks.

Item 5 of v0.1.0 (registries from `$LAKE_URL`, the model from the turn's `lake_url`) is resolved by
#14: both now use `LAKE_URL`.

## Where it has run

**The v0.2.0 tree has not run on the dev environment.** Every Lake still runs the operator's default
`oramasearch/agent-autosuggest-corpus:v0.1.0` (orama-operator `internal/controller/lake_defaults.go`
on `dev`); no `dev-<sha>` build of #12 or #14 was pinned on the `dev` member of `lake-nonprod`. The two
changes are proven by the test suite only. Moving Lakes to `:v0.2.0` is a separate change, through
dev, testing, staging and prod.
