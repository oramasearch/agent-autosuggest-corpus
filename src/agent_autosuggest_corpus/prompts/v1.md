# Auto-Suggest training corpus — prompt v1

Versioned because a prompt change is a model change.

---

You produce **training examples for the Auto-Suggest model**: given a business situation and its
data, what is worth building?

Each example is `(profile → project profile)`. Invent the profile, then answer it well.

## The output shape is fixed, and it matters

The `project profile` you produce is **the same shape the project-creation agent consumes later**.
Auto-Suggest proposes the approach; the project agent turns it into a Pipeline and chats about it.
One shape means the two compose instead of needing a translation layer that drifts.

Return ONE JSON object, no prose:

```json
{"profile_id":"kebab-slug","industry":"...",
 "persona":{"role":"...","context":"...","measured_on":["..."],"constraints":["must NARROW what a good answer is"]},
 "connections":[{"name":"...","kind":"postgres|bigquery|s3|rest|kafka","state":"captured|discovered"}],
 "tables":[{"database":"...","name":"...","rows":250000,
            "columns":[{"name":"...","type":"...","null_fraction":0.31}]}],
 "project_profile":{
   "suggested":[{"intent":"in the user's words","solution":"S-n","methodology":"gbdt|forecast|anomaly|uplift|retrieval",
     "why_this_data_supports_it":"name the columns","required_first":["..."],
     "pipeline_shape":{"connect":true,"clean":true,"point_in_time":true,"leakage_free":true,
                       "model":true,"calibrated":true,"holdout":true,"explain":"shap","serve":true,"act":true},
     "business_action":"who does what with the output","fits_the_constraint":"..."}],
   "declined":[{"intent":"...","reason":"...","answer":"capture it first | cannot be done"}]}}
```

## What makes the suggestion good

**Specific to THIS data.** *"Build a churn model"* is a category, not a suggestion. Name the label
column, the cutoff, the join. If you cannot point at the columns that make it work, do not suggest
it.

**Declining is a first-class output.** A model that always suggests something will suggest
something worthless. Include at least one declined item, and get the reason right — **discovered
but not captured** is answered *"capture it first"*, not *"cannot be done"*. They are different
failures with different fixes.

**Ordering is part of the answer.** Entity resolution before anything account-level. A churn score
is an *input* to next-best-action, not a competitor to it. Put those in `required_first`.

**A constraint must NARROW what a good answer is — or it is decoration.**

*"Must provide actionable insights"* narrows nothing; every suggestion claims that. A real
constraint says a **number**, a **prohibition**, or an **ordering**:

| Decoration | Real constraint |
|---|---|
| must provide actionable insights | can action **40** accounts a month and no more |
| must incorporate seasonality | orders lock every Tuesday and **cannot** change after |
| must optimize within budget | **no more than** 12 field visits per week |
| must be personalized | **never** shows a customer another customer's data |
| must focus on conversions | the team **only** works leads scored in the top decile |

Then `fits_the_constraint` says what about the **output** satisfies it — *"a ranked top-40, not a
score per account"* — not a restatement of the constraint itself.

**And `solution` is a catalogue id** (`S-1`, `S-5`, `UC-13`), never a sentence. The id is what lets
the project agent look up the correctness profile the pipeline must satisfy; a prose restatement of
the intent tells it nothing.

**A declined item's answer must match its reason.** *"Capture it first"* is only right when the
source is **discovered but not captured**. Data that genuinely lacks the shape — no label, no
timestamp — is not fixed by capturing it, and saying so teaches the wrong remedy.

**The constraints change the suggestion.** Someone who can action 40 items a month needs a ranked
top-40, not a score for every account. Someone who must explain any individual decision cannot be
handed an unexplainable model. Answer the situation, not the schema.

**The pipeline shape must match the methodology.** Churn: point-in-time, leakage-free, calibrated,
holdout, SHAP. Forecast: temporal validation and backtest, and **NOT calibrated** — there is no
probability to calibrate. Anomaly: unsupervised, threshold-governed, no label. Retrieval: indexed,
grounded, no supervised label at all. Getting this wrong teaches the neighbouring solution.

## Diversity

Every example should surprise someone who read the last one — a different industry, a different
shape of mess, a different number of sources, a different reason a task is impossible. If you
produce a structure you have produced before, pick something further away.

**Do not reuse an industry you are told has already been used.** Some are off-limits entirely
because they belong to the evaluation set, and training on them would make the eval meaningless.
